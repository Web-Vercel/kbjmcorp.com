# 两家虚构企业：数据隔离验收

## 执行范围

当前工作位于 `preview/tenant-isolation`，不推送会自动生成 Production 部署的 `next-rebuild`。用户截图已经证实原“开发分支”在 Vercel 实际是 Production 来源，不能继续把该分支推送视为纯预览。官网首页、导航、营销文案、品牌资产和共享样式均保持原样。

这一轮分三层：本地数据库断言、用户在隔离 Supabase 中执行同一套数据库断言、真实浏览器／客户登录验收。不要把第一层或第二层结果称为第三层已通过。

## 已准备的两个企业

| 对象 | 企业 A | 企业 B |
| --- | --- | --- |
| 名称 | 测试企业A · 星禾家居（虚构） | 测试企业B · 远舟科技（虚构） |
| 联系地址 | a@example.invalid | b@example.invalid |

| 资料 | 各自的项目、广告账户、合同、月报及财务工单 | 同类但独立的资料 |

所有联系方式、报告、费用、汇率和文件编号都是虚构的。账户状态不表示广告平台已连接；没有真实源文件。脚本中的资金只是测试行，不代表银行到账，也不执行支付或实际广告扣费。

## 数据库层：同一脚本，本地和托管测试库验证

文件：`supabase/tests/two-company-isolation.sql`。

它在一个事务内创建占位 Auth 行（没有密码、手机或可用登录凭据）、虚构公司和资料，然后切换数据库 `authenticated` 角色并模拟当前用户 claims，执行 42 项拒绝／允许断言。它不是 Supabase Auth 登录，不创建网站的身份切换接口，也不能证明短信或浏览器会话已通过。

检查包括：

- A 只能读取 A 的公司、项目、广告账户、余额、账目、开放合同、已发布报告、报告明细和工单；B 对称隔离。
- 猜到另一个公司的 ID 也不能读取报告、合同或提交对方的付款通知／财务工单。
- 客户不能直接提升自己的业务角色，不能访问内部 CRM 联系人与内部备注。
- 财务 viewer 可以读取本公司财务，但不能登记付款通知。
- 撤销财务授权后，业务成员身份仍在，财务资料立即不可见。
- 无公司授权的身份无访问权；员工 AAL1 无业务访问，授权管理员 AAL2 可以按内部职责访问两家公司。
- 撤销公司关联后，余额、公司和工单权限立即失效。

最后执行 **ROLLBACK**，包括临时 Auth 行、虚构账目、报告元数据及审计记录在内全部不保留。最终输出 `fixture_users=0, fixture_companies=0`。任何断言失败都会报错，不能跳过失败段或把 ROLLBACK 改成 COMMIT。相同占位 ID 如果已有数据，脚本直接停止，不覆盖或删除。若发现错误，提供错误提示，不重跑部分语句。

本地负向控制会故意在本地数据库放开公司读取策略，确认脚本能识别并报错；该放开策略不在托管执行文件内，不能应用到 Supabase。

## 用户在 Supabase 执行

1. 确认项目是之前新建的东京隔离项目 `ziijwwbcpuynkaxsbdvg`。
2. 打开 SQL Editor，新建查询，完整粘贴上述文件。
3. 只运行完整文件；不要使用“仅运行选中语句”，不要再运行初始化包。
4. 最后应显示两个清理计数均为 0；过程中不能有错误。若要核对 PASS 行，可查看前一个结果集。
5. 该文件可以保存为 `05 两企业隔离测试—自动回滚`，但并不会在管理员界面留下两家企业。

## 真实页面层（仍需单独完成）

为了让员工从现有界面查看可持续保存的测试企业，可由管理员在 CRM 中分别建立上述两家**另外的**测试档案，内部备注标明“虚构测试，不投放、不收付款”，开立余额为零的 CNY 钱包，不登记虚构银行到账，不将 SQL 测试余额当作真实充值。

客户真实登录验收要使用两个独立、受控的客户身份，各自经过现有授权流程，并在不同浏览器配置／隐私窗口中登录，不能复用管理员会话。当前短信和两个客户身份是否已配置未得到验证；不得通过设置手机为已验证或修改前端登录逻辑绕过身份服务。若采用 Supabase 支持的测试手机号／OTP 配置，只可用于此隔离测试项目，仍需实际 Auth 流程。

逐项验证：A 的列表不出现 B；A 手工输入 B 的项目／合同／月报／工单 URL，显示无权限或 404，不泄露内容；B 对称测试；退出后不可访问；撤销授权后原会话也不可继续读取。财务制单／独立复核继续使用独立员工身份，禁止共用管理员账号。

## 本轮页面加固

发现员工 RLS 本来可以广泛读取内部合同、月报，但客户页面也需要明确的当前用户公司范围。已对客户合同列表、合同详情和月报详情额外按 `finance_access.user_id=当前验证身份` 过滤，并显式限制已开放、非草稿合同和已发布月报。员工应在内部工作台查看内部资料，不能在客户视图中混入跨公司资料。没有授权时不查询文档；范围读取失败显示不可用，不把失败当作授权或未知余额为零。

本轮无数据库迁移、权限策略变更或额外 Auth 登录方式。现有数据库 RLS 继续作为第二道限制，不依赖仅隐藏按钮。

## 本地命令

```sh
npm test
npm run typecheck
npm run build
```

本地数据库测试使用 PostgreSQL 引擎执行上述整份脚本，并检查清理和负向控制；页面测试验证具体公司／财务范围过滤、未发布资料保护和合法访问。只有用户在托管库执行后，才能记录托管数据库层验收；只有实际两个客户登录后，才能记录真实会话验收。
