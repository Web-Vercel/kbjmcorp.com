# 公司间核销撤销与重新登记

已有 001–029 的项目，在 Supabase SQL Editor 新建「26 公司间核销撤销与修订」，执行 `supabase/migrations/030_upstream_payment_reversals.sql`。迁移新增空的撤销申请/独立复核表，替换核销统计及后续登记校验，不自动创建申请、不改变原始付款记录或客户余额。现有项目不要执行完整 bootstrap。

## 操作流程

在 `/zh/operations/upstream-payments` 的已通过记录下，具有财务制单权限的人员可申请“整笔撤销错误核销”，提供原因、影响、原件归档参考及 SHA-256。支持整笔批量分配的撤销；不能由浏览器指定负金额或挑选一部分分配撤销。

待复核期间，原核销继续生效，采购待核销额不提前释放。具有财务复核权限的另一账号独立核对后，可通过或退回。管理员同样不能自审。退回保留原核销；申请补充后另存撤销申请版本。通过后，本笔所有原分配从“已复核核销”统计退出，采购待核销额整体恢复。

原到账、分配、审批和撤销记录始终保留。原银行资金不会因撤销而退回，恢复的待核销额不是再次汇款指令。若实际到账确认有效，应沿用原银行流水号，在同一企业内登记下一付款版本、提供更正后原件依据并重新分配，再由另一账号复核。新付款版本通过前不计入已核销。

本轮仅更正系统内的核销对应关系，不执行银行退款、客户余额调整、发票更正或会计分录冲正。跨企业更正、溢付及银行退款需独立流程，不能用虚假净到账或负数分配代替。

## 状态、并发和幂等

- 撤销申请及复核表无认证用户直接写权限，记录不可修改或删除；所有函数检查 MFA、员工职责及企业范围。
- 同一付款只允许一个待复核撤销，且最多一次生效撤销；被退回可追加新申请版本。
- 撤销申请带固定请求 UUID，原内容重试返回同一申请。重复复核的相同账号、决定和说明返回原结果；改变历史结果会冲突。
- 复核先锁原付款，再按确定顺序锁其全部账单。新付款复核采用相同行锁顺序，并在计算可用采购额时排除已生效撤销，防止重复核销或批次部分生效。
- 待复核撤销优先显示在到账核对记录列表；每笔展示最近10个撤销申请，并对更早历史明确提示。页面保留原审批及撤销状态，不能把撤销理解成原银行交易被删除。
- 030 未执行时，029 的读取和登记仍可使用；服务端返回的 `reversal_enabled` 决定是否提供撤销表单，不宣称数据库已支持新流程。
- 撤销表单和撤销复核启用30秒等待上限。超时/网络异常提示保存结果未知，保留内容并要求核查原记录；不自动重试。通用表单的其他调用保持原等待行为。

## 验证

数据库测试覆盖待复核和退回不释放采购额、整笔生效后精确恢复各账单核销额、重新登记原银行参考号的新版本、旧原审批重试不会恢复已撤销金额、唯一生效撤销、权限/MFA/自审禁止、原记录不可变及客户钱包数量不变。接口测试排除浏览器金额，组件测试覆盖申请、独立复核和迁移前状态；超时测试核实重试请求信息和原输入不丢失。所有写入仅在隔离的虚构测试数据库进行。
