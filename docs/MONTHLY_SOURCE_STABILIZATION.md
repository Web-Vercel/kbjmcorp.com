# Preview delayed monthly source verification

Apply `061_monthly_source_stabilization.sql` only to Preview after 060, then apply `062_monthly_statement_adjustments.sql`, then deploy the Preview branch. No account authorization, first month, fee policy, wallet, invoice or global execution flag is enabled or changed by the migration. Existing prepared drafts have no new verification proof and remain eligible only for human handling; automatic release rejects them.

The fixed consumption period uses the advertising account timezone, with an exclusive next-month midnight boundary. Scheduled jobs become eligible at least six elapsed hours after account-local month-end. A first complete source read records immutable evidence and waits. A subsequent complete read at least twelve elapsed hours later must match the normalized account/period/currency/timezone, all daily amounts and metrics, and monthly totals. Transport metadata/raw-response hashes are retained as evidence but excluded from semantic equality. Daily rows are sorted, so row order alone does not create a difference. A changed source restarts waiting. The fifth nonmatching observation stops automatic attempts and requires manual handling. Invalid or unavailable sources use the existing bounded retry path; they are never treated as zero activity.

Draft completion is protected in the database, not just in the worker: the service cannot call the private legacy completion core and must present the verified report fingerprint. Publication independently verifies the same proof and all existing rate/FX/coverage/duplicate/available-funds checks. Matching observations are a readiness heuristic, not an OpenAI guarantee of finality. No original OpenAI invoice is downloaded or reconciled by this feature.

The scheduler is separate from the minimum wait: existing daily schedules will produce longer waits. To use two-hour sweeps for the current two-account Preview registry, execute `supabase/operations/reschedule_preview_monthly_verification.sql` in Preview. It changes only the existing named cron schedule, retaining its Vault authorization and URL. Inspect the returned job row. No row means the existing job must first be configured; do not count that as successful activation. No Production change is included. The scheduler remains bounded to two accounts per invocation and must be replaced with a paged queue before expanding the registry at scale.

For a Vancouver account in November (PST), December 1 00:00 local closes November. The first eligible read is December 1 06:00 local (Beijing December 1 22:00). A second matching read cannot qualify before December 1 18:00 local (Beijing December 2 10:00). Actual cron timing, hosting, FX and source availability can push processing later. Source changes or human review can postpone publication by days. No promised bill delivery date is inferred from eligibility.

Published automatically released statements from the last 90 days enter a leased source recheck queue. When an account has no preparation job to run, a sweep rechecks at most one eligible published statement; a statement is not rechecked more often than once per 24 hours. This is bounded periodic monitoring, not a promise to discover every historical change immediately. Failed retrievals are persisted as uncertain. Changed sources create immutable, deduplicated difference records linked to the original statement and source; the original statement and ledger remain unchanged. Any unresolved difference blocks later automatic publication for the same binding. The automatic-settings verification section shows the difference, and the billing overview shows a manual-investigation alert.

Difference records start as pending manual investigations. Migration 062 adds an explicit correction workflow: a finance preparer records evidence and generates a draft; SQL recalculates the corrected target using the original immutable quote's fees and FX and subtracts the original bill plus all already-posted corrections. A different finance reviewer approves or rejects it. An administrator separately publishes it; the available-funds and configured fictional-test scope checks remain mandatory. Positive differences debit prepaid funds; negative differences credit prepaid funds (not bank refunds). Zero-value corrections close verified nonmonetary changes without creating a ledger entry. The correction has its own immutable ID, review and publication receipt. Clients can view published related adjustment documents from the original bill; internal evidence/FX is not exposed.

Publication is idempotent and transactional. A newer source difference or another posted correction invalidates an older unposted draft. Published corrections resolve their source case and earlier cases for that bill; the monitor then compares against the corrected source baseline. A later reversion is a new case under a new baseline epoch, not a duplicate of an old closed case. Original bills and original ledger entries are never rewritten. No automatic correction, automatic bank transfer or automatic refund is added.

Read-only status is organization-scoped; worker functions and evidence writes remain service-only. No fake human reviewer is created, and email/SMS notifications are not added.

Checks: focused PGlite integration covers first-read blocking, minimum spacing, daily-content changes, persistent instability, verified publication, post-publication difference deduplication and unchanged ledger. Native PostgreSQL acceptance additionally covers concurrent releases and disputes/rate changes, using explicitly seeded earlier observations only in the disposable local test database. Hosted timing and complete client-role acceptance still require a separate Preview run.

The correction workflow adjusts the client's prepaid ledger and publishes a related client document. It does not silently recalculate agent commissions or rewrite previously allocated intercompany receipts/procurement records; finance must reconcile those downstream effects separately against the correction evidence.
