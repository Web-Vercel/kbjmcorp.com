# Preview 的两个客户邮箱登录验收

## 为什么需要独立测试入口

用户在托管 Supabase Phone 设置中确认没有可见测试号码选项，实际大陆短信服务尚未接通。继续使用两个虚构企业做页面隔离验收，可以使用两个独立的、由项目所有者创建并确认的邮箱密码客户身份。正式客户的手机号登录方案保持不变。

这不是假验证码、模拟 Cookie、修改手机为已验证或绕过 Auth。入口调用真实 Supabase `signInWithPassword`，仍需安全验证、持久限流和公司授权；不会注册用户、写 memberships、开钱包或提升角色。不作为手机号收信及所有权验证的替代验收。

## 强制条件

- 部署运行环境 `VERCEL_ENV` 必须恰好为 `preview`；Production 即便误设置启用标志也返回 404。
- `CLIENT_EMAIL_TEST_LOGIN_ENABLED=true`，默认 false。
- `CLIENT_EMAIL_TEST_USER_IDS` 必须是两个不重复的真实 Auth 用户 UUID，以英文逗号分隔；空白、重复、无效或多余身份都会拒绝开放。
- 沿用已经配置的 Supabase 公开／服务器连接、Turnstile 和 HMAC 持久限流。任何一项不完整，入口不开放。
- 成功密码登录后，Supabase 返回的身份必须有已确认邮箱，并且在上述两 ID 中。
- 任何 `staff_members` 身份（包括非活跃员工）均不能使用此客户测试入口；不要把总管理员 ID 加入列表。
- 每个测试客户必须事先仅关联一家企业；无公司或同时关联两家都拒绝进入。角色、公司不能由登录请求里的字段决定。

允许名单限制的是这个应用入口；它不是 Supabase 全局禁止其他 Email Auth 登录的配置。真正的数据权限仍由 memberships、finance_access 和 RLS 决定。禁止为测试账号授权真实客户企业。

## 用户配置顺序

1. 在现有东京独立测试项目中，通过 **Authentication → Users → Add user → Create new user** 建立两个客户测试邮箱身份。使用本人控制的邮箱及独立密码，确认邮箱；不要加入 staff_members。若使用 Gmail，两个本人邮箱别名（如 `yourname+testa@gmail.com`、`yourname+testb@gmail.com`）可用于测试，但仍是两个独立 Supabase Auth 身份。
2. 记录 A、B 的 User UID。不要分享密码。由管理员通过现有客户权限页面，把 A 只关联测试企业 A、B 只关联测试企业 B，初期使用只读业务权限。
3. 若要查看余额、合同和月报，再通过现有 CRM 客户财务授权把各自设为本公司的财务 viewer。不要授予 staff/admin 角色；只读用户不能提交充值通知，这属于预期权限。
4. 在同一个 Vercel 项目的 **Preview** 环境增加两个变量：`CLIENT_EMAIL_TEST_LOGIN_ENABLED=true`；`CLIENT_EMAIL_TEST_USER_IDS=用户A的UID,用户B的UID`。不要手工新增或覆盖 `VERCEL_ENV`；它由 Vercel 提供。
5. 部署独立的 `preview/tenant-isolation` 分支，不部署或合并到 Production 来源 `next-rebuild`。在 Turnstile 中允许实际新 Preview 主机名。重新部署生成的 URL 可能不同。
6. 两个客户分别使用不同浏览器配置或不同浏览器的隐私模式，访问 `/{locale}/test-login`。同一浏览器的多个隐私窗口可能共用一个会话；不能据此当作两个独立身份。管理员使用第三个独立会话。
7. 通过真实邮箱密码及 CAPTCHA 登录后，进入现有 `/{locale}/account`。客户不能进入员工后台。逐项验证各自公司资料、余额、开放合同、月报及工单；手工输入另一公司的 ID／URL也不能看到对方内容。
8. 对“没有报告”与“看不到其他企业报告”分别验证。当前尚未接通正式报告发布，不要往真实钱包中录入假到账，不能因为没有报告就宣称报告隔离的真实页面验收已经完成；数据库回滚脚本提供独立的虚构报告权限检查。

正式手机号页面不增加邮箱测试按钮，首页导航与品牌不变。直接测试入口不索引、不公开链接。关闭时，先退出两个测试会话并撤销测试企业关联／财务权限，再关闭此标志；必要时在 Supabase 禁用这些专用测试身份。仅关闭登录入口不会自动撤销已经存在的 Auth 会话或数据库授权。

## 当前完成与待验收

已实现条件门禁、真实 Auth 调用、已有员工排除、单公司授权检查、失败退出及不泄露凭据的错误处理。密码在提交后清空；不记录邮箱密码、验证码或 Cookie。没有数据库迁移、生产认证修改或真实短信发送。

真实用户尚未创建、允许名单尚未配置、客户登录与托管页面隔离尚未验收。代码／模拟供应商测试通过不等于这些托管步骤完成。

本轮验证：完整回归 304 项通过；随后补充的登录清理失败场景通过（API 文件最终 11 项通过），TypeScript 与生产构建通过。默认关闭页面／接口 4 项 HTTP 检查、客户入口 14 项和员工入口 25 项浏览器检查通过。没有在托管环境执行测试客户密码登录；真实账号、允许名单、公司授权和新 Preview 主机名仍需配置及验收。首页及正式手机号登录文件没有改动。
