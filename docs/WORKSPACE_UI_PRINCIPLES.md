# Business workspace UI and copy principles

Owner direction, 2026-11-14 (America/Vancouver). Applies to Preview and Production design. Implement and review on Preview before an authorized Production release.

- Each visible message must answer a user question: what happened, what is pending, who is responsible, what can I do, or what will my action change?
- Do not expose database, RPC, migration, persistence, branch, commit, deployment, locking or implementation commentary as routine business instructions. Keep engineering explanations in technical documentation. Optional administrator diagnostics must be explicitly labeled and collapsed.
- Prefer brief everyday language. Retain precise amounts, currencies, dates, scope, role boundaries and meaningful error states.
- Show status, critical numbers and the primary next action first. Put history, identifiers, sharing controls and occasional explanations behind named disclosures.
- Use labeled status dots consistently. Never infer completion from unavailable data or represent a role assignment as proof of user acknowledgement.
- Keep fictional/test/nonpayable labels visible. Keep material debit consequences, insufficient-fund warnings, independent review and actual confirmation controls visible at the point of action.
- UI simplification must not change access rights, calculations, saved records, review independence, publication or payment behavior.
- Avoid duplicate status indicators, repeated instructions and marketing navigation inside authenticated workspaces.
