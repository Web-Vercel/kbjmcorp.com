# 三个真实业务账号

本方案使用真实 Supabase Auth 邮箱密码账号、真实业务记录和指定企业权限。旧 `/demo` 及 `DEMO_*` 配置仍属于虚构演示，不会自动成为真实用户。三个邮箱由所有者提供，单独保存在开通清单，不写入迁移。

| 角色 | 可用功能 | 范围限制 |
| --- | --- | --- |
| investor | 查看企业概况、余额、已发布账单摘要、明确交接的广告来源摘要 | 只读指定企业，不显示原始 API、密钥、内部汇率或利润 |
| client | 查看自己企业账单，提交到账通知及客户问题 | 通知不增加余额，不能审核或发布账单 |
| sales | 客户资料跟进、客户阶段更新、非账务客服回复 | 只限指定企业，不能处理资金、财务问题或员工权限 |

全部账号要求验证器 MFA。权限在数据库重新检查，不依赖网页隐藏按钮。这些身份不写入传统机构级员工或成员授权，避免扩大为全客户权限。账号不能同时持有冲突的传统授权。

## 开通步骤

1. 在已有 001–037 的数据库，仅运行 `supabase/migrations/038_scoped_live_accounts.sql`。不要重跑新项目 bootstrap。
2. 等最新 Preview 部署完成，先退出旧演示会话。最高管理员完成 MFA 后进入 `/zh/admin/role-accounts`。
3. 逐个填写所有者提供的邮箱、初始密码（至少16字符）、角色，并明确选择 Kenny Lu / ReMax 对应企业。核对真实企业名称和 UUID，不能选测试企业。
4. 新建用户要求所有者确认已独立核实邮箱归属。创建接口将邮箱标记为已验证，不发送邀请邮件。初始状态为暂停。
5. 若用户已存在，用已有 Auth UUID 和匹配邮箱登记。创建后如关联失败，页面会显示已创建 UUID；按该 UUID 补登记，不重复创建。
6. 刷新列表，核对企业与角色后激活。账号在 `/zh/access/login` 使用邮箱与新密码登录，并设置验证器。
7. 在 Preview 验收角色权限、跨企业拒绝、暂停后旧登录拒绝，再单独安排 Production 发布。旧 DEMO JSON 密码不能用于这些真实账号。

管理员创建依赖部署服务器已有的 Supabase 服务端管理密钥。缺少配置时不会创建用户，不能把密钥填写到网页或聊天中。Auth 创建和业务授权跨服务，无法原子完成；部分完成状态需要按页面 UUID 恢复。

## 暂停与恢复

管理员在同一页面暂停或恢复账号，并填写原因。数据库每次检查活动状态与 Auth 会话创建时间。暂停立即拒绝受限业务访问；恢复后，旧会话仍被拒绝，必须重新用密码登录。Auth 禁用、删除会话、邮箱变化、冲突授权同样拒绝访问。操作保留审计，不删除账单或跟进记录。

这些是实际业务账号：客户通知和销售回复会持久保存；不录入虚假到账、不用修改密码清账。投资人只读，另外两种角色的合法操作会改变真实资料。
