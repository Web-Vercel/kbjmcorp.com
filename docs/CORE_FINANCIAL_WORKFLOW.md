# 核心业务：来源报告、对公收款与客户账务同步

## 业务边界

KBJM 加拿大负责广告账户对应关系、平台来源报告和费用说明；中国运营公司负责客户关系、合同原件、对公收款、人民币结算和财务复核；客户查看自己的已入账资金、月报、服务使用情况，并可登记付款通知。平台记录业务预付款，不是银行存款产品或广告平台实时余额。

合同原件不要求上传到 SaaS。由签约双方在受控档案中保存。平台后续登记合同号、主体、有效期、状态、原件保管负责人及档案编号；档案位置只给授权员工。费用约定需独立版本、生效日期、客户确认依据，不能通过改合同全文回溯改变历史费用。现有 UUID 是内部记录编号，不能冒充合同号。完整合同详情保留兼容访问和权限保护，客户资料页不再提供全文入口。暂停执行虚构合同造数脚本，后续验收围绕资金和报告。

## 核心记录与不变量

- 付款通知不是到账。银行实际到账核实后制单，由另一位具备权限且完成 MFA 的人员复核。银行流水去重，重复审批不重复入账。
- 余额 = 所有已入账、有符号流水金额之和。金额采用整数分，汇率采用精确十进制与明确舍入规则；不使用浮点数计算钱款。
- 报告同步、费用确认、报告发布、费用入账必须区分。现有内部对账审批不等于月报已发布或钱包已扣费。
- 不以最近100条明细推算总余额，不以没有报告推断当月花费为零。不把已发布报表金额直接当成已扣款金额。
- 已入账记录不覆盖、不删除。差错采用关联原记录的冲正与更正流水，须独立复核；不提供任意修改余额。
- 收费没有统一默认10%。依据客户明确接受的费率与生效版本计算，广告费、汇率和服务费分别披露。
- 客户只能读取自己获授权企业的数据。加拿大投放人员不自动获得中国收款资料；客服不自动拥有财务写权限。

## 开发顺序与验收门槛

1. **收款闭环验收**：两个虚构客户、不同财务制单与复核账号。覆盖重复流水、重复点击、同人自审、金额不符、未批准及事务失败。断言只有成功复核才影响余额。先用虚构银行依据，不发起真实付款。
2. **报告来源与核对**：私有保存平台原件，校验摘要、客户广告账户、币种、月份、时区及版本。中文说明保留原始数值与版本关系；翻译不修改金额。先支持人工导入，不假定已有 OpenAI 广告报告 API。
3. **月度费用入账闭环**：锁定来源版本、已确认收费约定和汇率，独立复核。发布与扣费在一个原子事务内，加入唯一业务键、并发锁与重试保护。修正版只记差额或冲正后重记，不能再次扣全部金额。余额不足时先进入人工处理，不擅自追加扣费或声称已暂停外部投放。
4. **对账与差错**：每日核对银行实际到账、批准收款、账务流水；按月核对原始报告、人民币结算与客户费用流水。差异生成待处理项，查明后通过冲正审批解决。退款独立设计和审批，不能用负数充值模拟。
5. **上线前**：托管测试库真实会话、跨企业访问、权限撤销、异常重试与恢复演练；操作记录可追溯后再经确认进行小额真实业务验收。

## 客户页面重点

已入账余额、累计到账、待核对付款、各月广告费及服务费、费用截至日期与入账状态、收支明细、中文报告、报告问题反馈。后续每笔费用可追溯来源报告及结算记录。月报和账务可能有时间差，必须标明状态，避免用户误以为实时余额。

准确性通过权限、整数账务、独立复核、去重、原子事务、对账及可恢复流程保障；不能承诺软件或人工操作永不出错。发生差异要明确显示并停止相关自动处理，不能把未知金额显示为零或隐藏差错。
