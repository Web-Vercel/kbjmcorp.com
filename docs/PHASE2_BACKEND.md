# 第二阶段：后台基础与本地验证

## 本轮范围

已实现代码：
- 内部工作总览、咨询筛选、咨询详情、追加内部跟进记录、更新跟进状态。
- 原子、幂等的“咨询转客户公司”：同时建立公司和联系人；手机号咨询不再被 CRM 必填邮箱限制。转换不创建 Auth 用户，也不分配客户成员权限。
- 建立内部项目、选择公司、可选关联同公司的广告账户、记录计划预算与币种、更新内部进度。
- 管理员按平台唯一 ID 保存广告账户归属；新关联始终为“未验证连接”，不伪造同步日期。内部操作员可以跟进业务，但不能新建外部账户关联。
- 内部邮箱/密码登录与验证器 TOTP 二次验证；与客户短信开关分离。业务 API 和数据库 RLS 都要求有效内部角色及 `aal2`。
- 自动追加操作记录，记录操作者与状态/归属元数据；不复制咨询正文、联系方式、跟进内容或凭据到审计载荷。
- 广告读取适配器接口及同步记录结构；没有编造供应商 API 端点，没有真实接口实现，没有修改预算、付款、创建广告或启停投放的方法。

本轮不包含：客户成员分配界面、文件/素材上传和审批、客户项目看板、真实报告导入、自动广告同步、内部人员管理界面或认证恢复流程。这些属于后续迭代。公开咨询防刷、正式隐私条款、保留/删除和恢复流程也需在真实业务开放前完成。

## “本地测试”与页面预览的区别

按用户选择，本轮没有创建独立 Supabase 云项目、购买短信或写入真实客户资料。

- `npm test` 在隔离开发环境内运行：业务 API 使用身份/供应商测试替身，SQL 在 PGlite PostgreSQL 引擎中执行。数据库内容仅供测试，不是正式资料库。
- `/{zh|en}/admin-preview` 是可公开查看的**只读演示**，所有公司和项目均为虚构，刷新不会变更任何业务数据。
- `/{zh|en}/admin` 及下级路径是真实后台代码，配置缺失时不会开放数据；匿名访问跳转到内部登录。它不是一个可绕过认证的“演示管理员账号”。
- 要手动验证真实登录、MFA、持久化 CRUD，需要后续接入选定地区的测试后端及测试身份服务。本地测试结果不等于托管服务、真实短信或大陆网络联调通过。

## 工作路径

| 路径 | 用途 |
| --- | --- |
| `/{locale}/admin-preview` | 无真实资料的只读演示 |
| `/{locale}/admin/login` | 内部邮箱/密码登录 |
| `/{locale}/admin/security` | 验证器设置或验证 |

当前列表采用初始容量限制，后续需补充分页和大规模检索。后台显示时间明确采用 America/Vancouver；计划预算不进行跨币种求和。

## 本地验证命令

在 `/workspace/kbjmcorp-next`：

```sh
npm ci
npm test
npm run typecheck
npm run build
npm run start -- --port 3016
```

另开终端，对没有配置真实服务的本地实例运行：

```sh
SMOKE_BASE_URL=http://127.0.0.1:3016 SMOKE_EXPECT_UNCONFIGURED=1 npm run test:smoke
SMOKE_BASE_URL=http://127.0.0.1:3016 SMOKE_EXPECT_UNCONFIGURED=1 npm run test:admin
```

`test:admin` 使用环境已安装的 Chromium；可用 `CHROMIUM_PATH` 选择其他可执行文件。仅在确定未配置服务的本地实例设置 `SMOKE_EXPECT_UNCONFIGURED=1`，避免对已配置实例提交测试凭据。脚本生成 `/tmp/kbjm-admin-desktop.png` 与 `/tmp/kbjm-admin-mobile.png`。

证据：105 项自动化测试、生产构建（含 TypeScript）、33 项公开站点检查、28 项内部路由/浏览器预览检查通过。数据库测试覆盖客户跨公司隔离、非内部成员拒绝、MFA 层级、手机号转客户的幂等性、备注作者约束、审计写保护、外部账户去重和跨公司关联约束。官方 SSR 客户端的 OTP 会话、MFA 升级 Cookie 与退出流程使用测试供应商响应验证。

## 后续接入测试环境

数据库与身份接口目前采用 Supabase 兼容结构：Auth 用户/会话、PostgREST、`auth.uid()` 与 `auth.jwt()`。如果未来选择境内普通 PostgreSQL，需部署兼容服务或实现后端适配，不能仅替换数据库 URL。存储地区、真实资料处理范围及跨境安排仍须先确定。

接入选定的独立测试服务时，先审阅并顺序运行迁移 `001`–`005`。迁移 `005` 增加内部成员、跟进记录、项目、同步记录和审计，以及相关 RLS/RPC。已有数据库若存在重复外部账户或不符合联系人约束的历史数据，应先处理冲突，不可删除用户资料来强行通过。

配置沿用 `.env.example` 中的服务端连接及安全设置。内部登录使用 Email/Password、CAPTCHA、共享持久化限流及 TOTP；客户短信是否启用由 `SMS_AUTH_ENABLED` 单独控制。TOTP 的真实开户、扫描、会话刷新与 HTTPS Cookie 仍需实际服务验证。验证器丢失后的受控恢复流程尚未实现；不可通过取消 MFA 检查绕过恢复。

### 内部管理员开通

没有公开管理员注册或自动提权逻辑。由可信环境管理员在选定测试身份服务中创建并核实测试用户后，通过受控数据库管理渠道加入：

```sql
-- 将占位符替换为已核实的 Auth 用户 UUID；不要直接执行占位符。
insert into public.staff_members(user_id, role, active)
values ('REPLACE_WITH_VERIFIED_AUTH_USER_UUID'::uuid, 'admin', true);
```

内部账号首次登录后设置验证器。客户 `memberships.role`、用户自行填写的 profile/user_metadata、邮件地址或手机号本身都不能授予内部权限。`operator` 是内部业务人员，当前可查看跨客户业务记录；外部客户仍只可读取所属公司数据。

## 真实广告账户后续对接

用户已提供一个真实加拿大广告账户作为后续验证样本。其真实名称、唯一 ID、凭据和数据不写入公开演示或测试夹具。

1. 通过受控方式取得并核实平台唯一账户 ID、归属及实际可用接口/导出权限。
2. 在管理员二次验证后保存该账户与客户公司的关联；这只是归属记录，不能标记为连接成功。
3. 根据实际开放能力实现 `src/lib/ad-platform/types.ts` 中的只读适配器。先验证账户，再读取广告项目和可取得的指标。
4. 同步任务记录来源、结果、时间和导入条数。只在真实验证/同步成功后由可信服务更新连接和同步状态。
5. 检查币种、平台时区、日期和归因口径；不伪造字段，不把“接口不支持”显示为“数据为零”。
6. 真实广告提交、预算变更、付款和启停均不在本轮代码能力范围。

所有真实配置需通过安全渠道提供，不在聊天、Git 提交或公开页面粘贴密码、验证码、二维码、密钥或客户资料。本轮没有触达真实广告账户，也没有执行托管数据库迁移。
