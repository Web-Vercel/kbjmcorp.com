# 客户付款通知回执与未知结果处理

沿用001–037，无新增SQL或审批。原request_client_topup函数已返回通知UUID，并以钱包+付款参考号唯一约束防重复；本次只使用该返回值，不改变数据库。

API仅在RPC返回有效UUID时确认通知已保存，并返回noticeId、pending及ok。不信任客户端传入的到账状态或币种；无效回执返回502，前端作为结果待核查处理。通知保存不创建钱包流水，也不表示银行到账。

表单保持并发点击锁，新增30秒超时、有效编号回执及通知定位链接。成功后显示本次金额和参考号，刷新读取实际通知及余额；只能经显式“登记另一笔实际付款通知”重新填表。没有立即清空未知结果或乐观增加余额。409提示先核对原通知/金额，不换参考号或再次付款；401/403保留原输入并提示登录/授权；429提示先核查现有通知上限。超时、网络错误、5xx或不完整成功响应明确为未知，保留原金额、参考号和确认，不自动重试。原参考号唯一约束仍承担重复保护，不宣称可用新参考号安全重试。

公开演示回调单独标记虚构，不调用真实接口、不发起付款、余额不变。正式回执不是收款凭证；财务实际到账核实、独立复核及后续月结仍沿用原流程。

验证：30项当前测试通过，包含付款API/表单、演示余额不变、隔离银行到账验收及001–037完整业务贯穿。4项本地Chromium场景覆盖中英文×375/1440宽度的有效回执、重复参考号及503未知结果；接口均为虚构响应，没有真实付款或财务写入。类型检查与Next构建通过。
